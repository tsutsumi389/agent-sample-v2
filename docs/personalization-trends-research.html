1. エグゼクティブサマリー

結論: 現在の実装は2026年のトレンドの「中核部分」に概ね沿っている。
ハイブリッド記憶（ホットパス＋バックグラウンド抽出）、構造化プロフィール、プロアクティブ想起という3本柱は、 Mem0 / LangMem / ChatGPT メモリ等が採用する標準パターンと一致する。 一方で、①記憶タイプの分類（エピソード／意味／手続き）、②時間メタデータと陳腐化管理、 ③ハイブリッド検索、④信頼度・出所の管理 がギャップとして残る。

長期記憶の項目設計については、現状の UserProfile（5項目）は良い出発点だが、 業界標準と研究事例を踏まえると 「アイデンティティ／専門性／応答スタイル／目標・進行中の文脈／制約」 を加えた拡張と、記憶アイテムごとの メタデータ（タイムスタンプ・信頼度・出所） の付与を推奨する（詳細は 第5章）。

2. 現在の実装の概要

2.1 アーキテクチャ

要素実装
スタックFastAPI + LangGraph（ReAct）+ LangMem + PostgreSQL（pgvector, 768次元）+ Ollama（gemma4 / nomic-embed-text）

3. 2026年のトレンド

3.1 記憶タイプの標準分類（CoALAフレームワーク由来）

2026年時点で、エージェント記憶は 3〜4タイプの分類が業界標準 になっている （Princeton の CoALA フレームワーク〈2023〉が起源。LangMem SDK もこの3分類を採用）。

タイプ保存するもの更新パターン
意味記憶（Semantic）事実・ユーザーの好み・属性・ドメイン知識。「ユーザーは何者か／何が事実か」上書き・統合（プロフィール型）＋蓄積（事実コレクション型）
エピソード記憶（Episodic）過去の具体的なやり取り: 何が起きたか・取った行動・結果・タイムスタンプ。事例ベース推論の材料追記のみ（イベントログ型）
手続き記憶（Procedural）「どうやるか」: 学習した対応パターン、フィードバック由来のルール。LangMemでは「エージェントが自身のシステムプロンプトを書き換える」形で実装フィードバック駆動で漸進更新
インコンテキスト記憶作業領域（会話履歴・ツール出力）。他タイプから「何を取り込むか」の設計が肝ターンごと

3.2 主要フレームワークの動向

フレームワーク特徴
Mem0（48k+ stars, $24M Series A）ベクトル意味検索が基本＋上位プランでエンティティ関係のナレッジグラフ。user_id / agent_id / session_id / org_id の4スコープ設計が特徴
Zep / Graphiti時系列ナレッジグラフ。事実に有効期間（valid_at / invalid_at）を持たせ、「変化を置き換えではなく進化として扱う」
Letta（旧MemGPT）OS風の階層記憶（core / recall / archival）。LLM自身が記憶階層を管理
LangMemLangChain純正。3記憶タイプ対応、ストレージ非依存。本プロジェクトが採用中

3.3 商用アシスタントの実装（参考になる実例）

ChatGPT は2層構造: ①「Saved memories」（明示的・ユーザー編集可能な事実リスト）＋②「Reference chat history」（過去チャットの暗黙的参照）。 さらに内部的にシステムプロンプトへ注入されるプロフィールは次のカテゴリを持つことが判明している:

  • Assistant Response Preferences — 応答スタイルの好み（口調・検証習慣など）
  • Notable Past Conversation Topic Highlights — 過去会話の主要トピック
  • Helpful User Insights — 居住地・趣味・ライフスタイル等のインサイト
  • User Interaction Metadata — デバイス・利用頻度・モデル使用統計

Claude は対照的に「プロフィール要約を作らず、生の会話履歴を都度検索する」透明性重視の設計 （conversation_search / recent_chats ツール）＋プロジェクト単位の記憶分離。 「要約プロフィール型（ChatGPT）vs 生履歴検索型（Claude）」という設計思想の対立軸が存在する。

3.4 検索（想起）手法の進化

2026年の大きな潮流は「純粋なベクトル類似検索からの脱却」。 最新システムは ①意味的類似度 ②BM25キーワードマッチ ③エンティティマッチ の3信号を並列実行し正規化・融合する。 リランキング（多段再スコアリング）とメタデータフィルタリング（構造化属性での絞り込み）もプロダクション必須要件とされる。

3.5 プロダクションで確立されたパターン

  1. 非同期書き込みがデフォルト — 記憶抽出が応答レイテンシに影響しない設計
  2. タイムスタンプ管理 — 時間情報のない記憶は時系列推論で破綻する
  3. 記憶の陳腐化対策 — 「高頻度で検索される古い情報が誤った確信度で保持される」問題への対処（信頼度・鮮度の管理）
  4. ユーザーによる可視化・編集 — ChatGPT / Claude とも記憶の閲覧・削除・オプトアウトを提供。プライバシー設計が差別化要因に
  5. 異なるライフサイクルの分離 — 「情報ごとにライフサイクルが違うため、同じ方法で保存・検索すべきでない」（arXiv:2510.07925）

3.6 研究面の知見（arXiv:2510.07925 ほか）

  • 三層構造（短期記憶=全文 → 要約 → 長期記憶=埋め込み＋LLM生成タグ＋タイムスタンプ）＋構造化JSONプロフィールの組み合わせで、検索精度がRAGベースライン比 +21.3%（LoCoMo, GPT-4o）
  • ユーザープロフィールを除去すると検索精度が最大7%低下 — 構造化プロフィールの有効性のエビデンス
  • プロフィールは「事前定義された空のカテゴリを持つ構造化JSON」をLLMが継続的に更新する方式（本プロジェクトと同型）
  • ベンチマークは LoCoMo / LongMemEval / BEAM が標準化。ただし大規模化（10Mトークン）で性能が約半減するなど、時間的抽象化・セッション間ID解決は未解決課題

4. トレンド適合性の評価

4.1 トレンドに沿っている点 準拠

観点評価
ハイブリッド書き込み（ホットパス＋バックグラウンド抽出）✓ Mem0等が確立した「非同期抽出をデフォルトに」のパターンに合致。after_seconds=2 の遅延実行も妥当
構造化プロフィール（Pydanticスキーマ抽出）✓ 「事前定義カテゴリの構造化JSONをLLMが更新」という研究・ChatGPT実装と同型。プロフィール有無で検索精度+7%のエビデンスあり
プロアクティブ想起（dynamic_promptでの毎ターン注入）✓ ChatGPT型の「自動注入」アプローチ。エージェント任せのツール呼び出しより安定（特にローカルモデル）という判断は合理的
ネームスペース分離（profile / memories × user_id）✓ Mem0のマルチスコープ設計の簡易版として正しい方向。蓄積型と上書き型のライフサイクル分離もトレンド通り
記憶の可視化・削除UI／API✓ 透明性・ユーザー制御のトレンドに合致

4.2 ギャップ 改善余地

観点ギャップ内容優先度
記憶タイプの分類「一般記憶」が意味記憶とエピソード記憶を区別せず混在。標準の3分類（意味／エピソード／手続き）に対し手続き記憶が欠落高
時間メタデータ記憶にタイムスタンプ・有効期間がなく、「先月引っ越した」等の時系列推論や情報の更新（古い好み vs 新しい好み）に対応できない高
陳腐化・信頼度管理記憶の鮮度・信頼度・出所（ユーザー明言か推測か）の概念がない。2026年の主要未解決課題として認識されている領域中
検索手法純粋ベクトル検索のみ。トレンドはベクトル＋BM25＋エンティティマッチの融合＋リランキング（ローカルデモの規模では実害は小さい）中
記憶の統合・重複排除一般記憶が無制限に蓄積。矛盾する記憶の解決・統合（consolidation）の仕組みがない（LangMemのmanagerに統合機能はあるが明示活用していない）中
スコープ設計user_id単位のみ。session/プロジェクト単位の記憶分離（Claudeのプロジェクト別メモリ、Mem0のrun_id/org_idスコープ）がない低

5. 推奨: 長期記憶に持たせるべき項目

業界実装（ChatGPT / Mem0 / Zep）・研究（arXiv:2510.07925, CoALA）・現実装の制約（ローカルLLM）を踏まえた推奨項目。 3記憶タイプ＋共通メタデータの構成とする。

5.1 構造化プロフィール（意味記憶・上書き型）— UserProfile の拡張

カテゴリフィールド案内容・根拠現状
アイデンティティ name名前・呼び名あり
locale言語・地域あり
timezoneタイムゾーン（日時表現のパーソナライズに必須）追加推奨
属性 attributes職業・所属・立場・家族構成などの安定属性あり
expertise専門領域と習熟度（例:「Python上級」「機械学習は初学者」）。説明の深さ・前提知識の調整に直結。研究でも「expertise level」は主要プロフィール項目追加推奨
嗜好 preferences好み・興味・嗜好（好きなもの）あり
dislikes嫌い・避けたいもの（NG話題・苦手な形式）。「やらないこと」は「やること」と同等に重要だが混在させると検索で埋もれる追加推奨
コミュニケーション response_style口調・詳しさ・形式の好み（ChatGPTの「Assistant Response Preferences」に相当）あり
communication_patterns質問の仕方の癖・検証を求める習慣・例示を好む等の対話特性任意
文脈 goals中長期の目標・進行中のプロジェクト（例:「資格試験勉強中」「アプリ開発中」）。「次に何を手伝うべきか」のプロアクティブ性の源泉。ChatGPTのsaved memoriesでも「ongoing projects」は中心項目追加推奨
constraints制約・配慮事項（アレルギー・利用環境・予算・時間制約など）。安全性・実用性に直結するため独立カテゴリが望ましい追加推奨
# 拡張版 UserProfile のイメージ（Pydantic）
class UserProfile(BaseModel):
    # アイデンティティ
    name: str | None = None
    locale: str | None = None
    timezone: str | None = None
    # 属性
    attributes: list[str] = []        # 職業・所属・家族構成など
    expertise: list[str] = []         # 専門領域と習熟度
    # 嗜好
    preferences: list[str] = []       # 好み・興味
    dislikes: list[str] = []          # 苦手・避けたいこと
    # コミュニケーション
    response_style: str | None = None
    # 文脈
    goals: list[str] = []             # 目標・進行中のプロジェクト
    constraints: list[str] = []       # 制約・配慮事項

5.2 エピソード記憶（蓄積型）— 現「一般記憶」の構造化

フリーテキスト1本ではなく、最低限のメタデータを持つレコードにする。 Zepの時系列グラフほど重くせずとも、タイムスタンプと種別だけで時系列推論・陳腐化判定が大きく改善する。

フィールド内容
content事実・出来事の要約（現状と同じ）
kindfact（意味的事実）/ event(出来事) / feedback(ユーザーからの指摘) の種別
occurred_at / recorded_at出来事の発生時期と記録時刻。「先週」「来月」等の相対表現を絶対日時に解決して保存
sourcestated（ユーザー明言）/ inferred（LLM推測）。信頼度の根拠になる
confidence抽出時の確信度（推測由来は低め）。注入時のフィルタやプロフィール昇格の判断材料
last_accessed_at最終想起時刻。陳腐化判定・容量管理（古く参照されない記憶の減衰）に使用

5.3 手続き記憶（フィードバック駆動・少数精鋭）

LangMemが「エージェントが自身のシステムプロンプトを書き換える」形でサポートする領域。 ユーザーからの修正・指摘（「箇条書きにして」「敬語はいらない」）を行動ルールとして蓄積し、 dynamic_prompt で常時注入する。response_style の発展形として、まずは 「interaction_rules: list[str]」をプロフィールに追加する程度の軽量実装でもトレンドの方向性は満たせる。

5.4 持たせるべきでないもの（アンチパターン）

  • 一時的・些末な情報（現在のINSTRUCTIONSで既に除外済み — 正しい設計）
  • 機微情報の無断推測（健康状態・政治信条・宗教等をLLMが推測して保存するのは避け、ユーザー明言時のみ・出所付きで保存）
  • 会話の生ログ全文（長期記憶は要約・抽出した事実のみ。生ログはcheckpointer側の責務）
  • アシスタント自身の発言由来の「事実」（ChatGPTがユーザーメッセージのみを記録するのは、誤った応答の内容が事実として固着するのを防ぐため）

6. 改善ロードマップ案

フェーズ内容工数感
Phase 1
優先度: 高		 ① UserProfile の拡張（timezone / expertise / dislikes / goals / constraints 追加）
② 一般記憶へのタイムスタンプ・kind・source付与（保存時メタデータ）
③ 抽出INSTRUCTIONSの更新（相対日時の絶対化、推測と明言の区別）		 小（スキーマ変更＋プロンプト調整が中心）

優先度: 中		 ① 記憶の統合・重複排除（LangMem managerの統合機能の明示活用）
② 注入時の鮮度・信頼度フィルタ（古い記憶の減衰、confidence閾値）
③ dynamic_prompt でプロフィールは全文注入・エピソードのみ検索、に分離（プロフィールは1オブジェクトなので検索不要）		 中
Phase 3
優先度: 低（規模拡大時）		 ① ハイブリッド検索（pgvectorのベクトル＋PostgreSQL全文検索の融合）
② 手続き記憶（フィードバック→行動ルールの自動学習）
③ プロジェクト／セッション別スコープの追加		 大
